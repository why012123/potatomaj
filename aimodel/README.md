# aimodel —— 土豆麻将的 AI 决策模块（日式三人麻将）

外层的 [`potatomaj`](../potatomaj) 解决「**把截图读成牌**」；这一层解决
「**读到牌之后该打哪张**」。方法是机器学习：先让神经网络模仿一个启发式教师
（行为克隆），再用自对弈强化学习（PPO）接着练。

整个模块只依赖 **numpy**（连 PyTorch 都没装）—— 一个 35 万参数的小网络，
手写前向/反向 + Adam 就够了，实测一次 minibatch 更新只要几毫秒。

```bash
cd potatomaj

# 打一局看看（神经网络 vs 两个教师）
.venv/bin/python -m aimodel.play

# 自己下场打
.venv/bin/python -m aimodel.play --human

# 拿一张雀魂截图问「打哪张」
.venv/bin/python -m aimodel.advise samples/sanma5.webp

# 从头训练（行为克隆 + 自对弈）
.venv/bin/python -m aimodel.train all --hands 5000 --matches 300 --iters 20

# 评测
.venv/bin/python -m aimodel.evaluate --matches 300

# 开一桌，三个人一起下（你 / 对话里的 AI / 脚本 AI）
./run-battle.sh
```

## 零、三人对战台（可人机同桌）

除了让 AI 自己打，还能**开一桌三个人一起下**：你手操一个位子、AI 助手一个位子、
脚本 AI 一个位子。

```bash
./run-battle.sh                      # 或者在 Finder 里双击「土豆麻将对战.command」
```

然后浏览器打开 `http://127.0.0.1:8765/?seat=0`：

* 你的手牌在下面（**真牌面图**，直接点牌出牌，数字键 1~9 也能选）
* 两家的手牌是牌背，**看不到彼此手牌**（每个座位只能拿到自己视角的 `/api/state`）
* 右侧实时牌谱，顶部显示剩余张数 / 巡目 / 宝牌指示，左下显示你的向听和进张
* 一个人等太久也不怕：超过 `--wait` 秒自动由教师托管，不会把局卡死

座位随便配：

```bash
SEATS=human,ml,teacher ./run-battle.sh    # 换成神经网络坐对面
SEATS=ml,ml,ml         ./run-battle.sh    # 纯 AI 自战，看热闹
```

三个座位的类型：

| 类型 | 谁在动 | 怎么接管 |
|---|---|---|
| `human` | 人 | 浏览器里点牌 |
| `external` | 外部程序 | `python -m aimodel.ui.assistant` 看局面 / `-p 3p` 出牌 |
| `teacher` / `ml` / `random` | 引擎内的 agent | 无需干预 |

`external` 座位是留给「对话里的 AI」的接口：轮到他时整局会挂起等命令，
`assistant.py` 就是他的操作面板（`--watch` 可以一直等到轮到自己）。
如果不想每手都人工回，`python -m aimodel.ui.autopilot` 可以把这个座位
交给训练好的网络托管，它打完还守着，下一次「再来一局」自动接手。

> 架构上就一句话：**引擎在后台线程里跑，需要人 / 外部决策时把那个线程挂住**，
> HTTP 服务照常响应；每个座位只拿得到自己视角的局面，所以谁都没法偷看。

### 观战 / 回放 / 局间确认（后端接口）

牌桌之外还提供这几个能力，Java 客户端（`aimodel/ui/java/`）就是接这些接口的：

| 能力 | 接口 | 说明 |
|---|---|---|
| **逐手回放** | `GET /api/replay` | 元信息：多少帧、几人、能不能全亮 |
| | `GET /api/replay?i=N` | 第 N 帧（**所有手牌都在**，回放就是要全亮） |
| | `GET /api/replay?from=A&to=B` | 批量取，客户端预取用 |
| **观战全亮** | `GET /api/state?seat=0&reveal=1` | 只在桌上**没有人类/外部座位**时生效 |
| **局间确认** | `POST /api/next` | 一局打完挂住，玩家点了才开下一局 |
| **铳牌标红** | 帧里的 `agari` | `{winner, loser, tile, tsumo}`，`loser` 那家的牌河里 `tile` 就是要标红的 |

**为什么要服务端记帧**：客户端 500ms 轮询根本抓不全每一手（一手可能只要几十毫秒）。
引擎每产生一条动作就记一帧完整局面（含四家手牌），一场约 200~800 帧，
内存一两兆，翻帧是纯本地操作。

**为什么「全亮」要设门槛**：`reveal=1` 只在没有真人座位时被接受 ——
否则观战的人能把别家手牌念给正在打的人听。这个判断在服务端，
客户端绕不过去。

## 零之二、八个模型：四种「得分条件」× 三麻/四麻

规则（怎么和牌、怎么算点）八个模型完全一样，**不同的只有它们在追求什么**。
这就像给八个牌手发不同的工资：

| 模型（当前 **v1.1**） | 人数 | 得分条件 | 教师口味 |
|---|---|---|---|
| `maj-normalv1.1` | 三麻 | 段位分 | 标准 |
| `maj-mountainv1.1` | 三麻 | 段位分 **− 3.0×放铳点数/1000** | 防守 |
| `maj-flashv1.1` | 三麻 | 段位分 **+ 4.0×和了局数** | 速攻 |
| `maj-hugev1.1` | 三麻 | 段位分 **+ 1.5×累计番数** | 大牌 |
| `maj-normal4v1.1` | 四麻 | 段位分 | 标准 |
| `maj-mountain4v1.1` | 四麻 | 段位分 − 3.0×放铳 | 防守 |
| `maj-flash4v1.1` | 四麻 | 段位分 + 4.0×和了次数 | 速攻 |
| `maj-huge4v1.1` | 四麻 | 段位分 + 1.5×番数 | 大牌 |

**版本**：命名跟着用户定的规矩 —— **原名称直接接版本号**（`maj-flashv1.1`、
四麻 `maj-flash4v1.1`）。**不带版本号的写法一律指向最新版**，所以老命令不用改：
`flash4`、`maj-flash4`、`maj_flash` 都能解析到 `maj-flashv1.1`。
旧版权重留在 `weights/*v1.npz`，纯克隆基线留在 `weights/*_bcbase.npz`（做对照用）。

实测结果（八项配对检验、风格对照、已知问题）在 [RESULTS.md](RESULTS.md) 第 5 节。

```bash
python -m aimodel.train --list-models          # 看八个模型和训练状态
python -m aimodel.train all --model maj-flash4 # 单独训一个
python -m aimodel.train_all --jobs 3           # 八个一起训（并行）
```

**为什么得分条件要这么设计**

* **段位分是所有模型的底子**（``(点数-返し点)/1000 + 顺位点 + 额外段位分``）。
  不挂这个底子，模型会学出「只要不点炮，垫底也无所谓」这种废策略。
* `mountain` 额外扣一笔放铳分，等于把点炮的痛感放大 → 它会更早弃和。
* `flash` 按**次数**给钱，逼它抢速度：小牌快和比大牌慢和划算。
* `huge` 按**番数**给钱，逼它做大牌：同样是和，三番和八番差别很大。

**教师口味也得配套**：追速度的模型就该跟「爱碰爱快的教师」学，不然行为克隆
第一步方向就是歪的。四套口味的参数在 `agents.STYLES`：

| 风格 | 弃和门槛 | 危险度 | 进张权重 | 打点权重 | 副露上限 |
|---|---|---|---|---|---|
| 标准 | 3 向听 | ×1.0 | 20 | ×1.0 | 3 |
| 防守 | **2 向听** | **×2.0** | 20 | ×1.0 | **2** |
| 速攻 | 4 向听 | ×0.6 | **26** | **×0.4** | **4** |
| 大牌 | 3 向听 | ×1.0 | 18 | **×2.5** | **2** |

## 零之三、四麻也支持

四麻不是「三麻多一个人」，差别都实现了：

| | 三麻 | 四麻 |
|---|---|---|
| 牌 | 108（万子只有 1m/9m） | **136（34 种全用）** |
| 吃 | 没有 | **有**（只能吃上家；碰/杠优先于吃） |
| 拔北 | 有 | 没有 |
| 北 | 永远不是役牌 | **北家手里北就是自风** |
| 三色同顺 | 数值上不可能 | 有（副露降番 2→1） |
| 王牌 | 18 张 | 14 张 |
| 不聴罰符 | 2000 | **3000** |
| 起始点 | 35000 / 返 40000 | **25000 / 返 30000** |
| 顺位点 | +15 / 0 / −15 | **+15 / +5 / −5 / −15** |
| 宝牌循环 | 1m↔9m 首尾相接 | 正常循环 |

跑一局四麻：

```bash
python -m aimodel.play --agents maj-flash4,teacher,teacher,teacher --players 4
python -m aimodel.ui.server --seats human,maj-normal4,maj-flash4,maj-huge4 --delay 1.0
```

## 零之四、在别的机器（服务器）上训练

`aimodel/` **只依赖 numpy** —— 没有 PyTorch、没有 CUDA、不需要显卡。
一台常年开机的机器直接 clone 下来就能训，这是当初刻意选的路线。

```bash
git clone git@github.com:why012123/potatomaj.git && cd potatomaj
./aimodel/train-server.sh                       # 一键跑完整一轮
./aimodel/train-server.sh --version v1.3 --hands 12000 --iters 30
./aimodel/train-server.sh --jobs 12              # 手动指定并行数
```

脚本会自己做完这几件事：

1. 缺虚拟环境就建、缺 numpy 就装
2. **按核数和内存自动算并行数**（克隆阶段每个进程要吃 1.5~2 GB 常驻内存，
   所以并行数同时受核数和内存限制，不是核越多越好）
3. 克隆 → 存纯克隆基线 `*_bcbase.npz` → 自对弈（带对手池）
4. 已训完的模型**下次自动跳过**，中断了可以接着跑

### 踩过的三个坑（脚本里已经处理）

| 坑 | 现象 | 处理 |
|---|---|---|
| **BLAS 线程爆炸** | 4 个进程各开满核数个线程，负载飙到 99，单进程反而更慢 | 每个训练进程限 1 线程（实测总吞吐 +22%、单进程 +30%） |
| **克隆阶段吃内存** | 6000 局样本 ≈ 1.5~2 GB/进程，开太多会被 OOM 杀掉 | 并行数按 `min(核数/2, (内存-2)/3)` 自动压 |
| **日志被覆盖** | RL 阶段会重写该模型的日志，看不到克隆阶段的留出率 | 克隆阶段的数字记得当场记下来（或用 `progress.py` 巡检） |

### 看进度

```bash
python -m aimodel.progress --version v1.3    # 每小时看一眼，走歪会自己报 ⚠️
tail -f aimodel/weights/logs/maj-flashv1.3.log
```

`progress.py` 会盯着**留出集一致率**（克隆有没有学到东西、有没有过拟合）和
**对教师段位分的走势**（强化学习有没有在往上爬），连续下滑会主动告警。

### 把结果拿回来

只需要传权重（一个 1~2 MB，八个模型十几 MB）：

```bash
rsync -av 服务器:~/potatomaj/aimodel/weights/*.npz ./aimodel/weights/
```

### 数据量参考（按机器规模选参数）

| 机器 | 建议 |
|---|---|
| 8 核 / 16 GB | `--jobs 4`，`--hands 6000`（一轮约 4 小时） |
| 16 核 / 32 GB | `--jobs 6`，`--hands 12000`，`--iters 30` |
| 32 核 / 128 GB | `--jobs 8`（**别再往上加**：8 个模型就是 8 个任务，多了没意义），把 `--hands` 提到 20000 |

### ⚠️ 并行数要分清「训练」和「产数据」—— 两者差 27 倍

| 场景 | 单进程内存（**实测**） | 并行上限 |
|---|---|---|
| **训练**（克隆阶段样本常驻） | 四麻 15000 局时约 **5 GB** | 受内存限制，32GB 机器 `--jobs 4` |
| **selfplay 产数据** | **~186 MB** | 16 个 worker 实测安全（峰值远低于 32GB） |

**曾经把「5GB」套到数据生成上，把并行数卡在 4，白白浪费了很多轮** ✗
产数据时该开 16 就开 16。

**但要注意收益递减**（实测）：

| workers | 吞吐 |
|---|---|
| 4 | 70,270 局/小时 |
| 6 | 97,048 局/小时 |
| **16** | **105,577 局/小时** |

**4 → 16 只提升 1.5 倍，不是 4 倍** ✗ 瓶颈不在 CPU 核数（机器 24 核），
而在**每个 worker 各自落盘/序列化 shard**。
所以要真提速得改 **shard 写入方式（批量缓冲）**，而不是继续加核。

**注意**：只有 8 个模型，所以并行数超过 8 是浪费。想再快只能加每轮的
`--matches`（自对弈场数）或者缩短 `--hands`。

## 一、三麻规则（默认对齐雀魂三麻段位战）

三麻不是「四麻少一个人」，规则差别不少。下面每条都对着官方资料核过，
有疑问的地方在代码里也标了出处：

| 项目 | 三麻的做法 | 代码 |
|---|---|---|
| 牌张 | **108 张**：去掉 2m~8m，保留 1m/9m、全部筒索、全部字牌 | `sanma.SANMA_TYPES` |
| 吃 | **没有吃**，只能碰 / 杠 | `engine.ACTION_TABLE` |
| 赤牌 | **赤 5p / 赤 5s 各 1 张**（没有赤 5m，因为 5m 不存在） | `sanma.AKA_TYPES` |
| 北 | **不是役牌**（客风），可以留在手里当普通牌；**拔北**算 1 张宝牌、**不是役**，所以只有拔北宝牌不能和牌 | `sanma.NORTH` |
| 拔北 | 从王牌补一张（可岭上开花）；**不翻新宝牌指示牌**；算鸣牌，会破一发/两立直/天和/地和/九种九牌 | `Rule.kita_flips_dora=False` |
| 王牌 | **18 张** = 8 岭上（杠 4 + 拔北 4）+ 5 宝牌 + 5 里宝，摸牌区 51 张 = 每人正好 17 巡 | `Rule.dead_wall=18` |
| 自摸 | **ツモ損**：子家自摸由「另一子家付 1a、亲家付 2a」，总额比四麻少一份 | `Rule.tsumo_loss=True` |
| 不聴罰符 | **2000 点**（四麻是 3000） | `Rule.noten_penalty=2000` |
| 多响 | **双荣和**（无头跳），供托归头跳；雀魂没有三家和了流局 | `Rule.double_ron=True` |
| 数え役満 | **13 番**起 | `Rule.kazoe_han=13` |
| 起始点 | 35000 / 返 40000，箱割れ（负分）立即结束 | `Rule.start_score` |
| 宝牌 | 指示牌 **1m→宝牌 9m、9m→1m**（万子只有 1m/9m，所以首尾相接） | `sanma.dora_from_index` |
| 三色同順 | **不可能**（万子没有顺子）；**三色同刻可能**（只能 1 或 9） | `sanma._score_normal` |
| 一気通貫 | 只可能靠筒 / 索 | 同上 |
| 途中流局 | 九种九牌、四槓散了 | `engine` |
| 食替 | 碰完不能立刻打刚碰的那张 | `Player.kuikae_tile` |
| 役 | 含国士、四暗刻、大三元、四喜、字一色、绿一色、清老头、九莲（纯正双倍）、四杠子、天和、地和 | `sanma.YAKU_CN` |

### 点数表逐格核对

这不是「差不多就行」的地方。我把雀魂游戏内那张**闲家点数表 / 庄家点数表**
（每格第一行是荣和收取点数，第二行是自摸时【闲家付, 庄家付】）
整张抄下来做成回归测试：

```
.venv/bin/python aimodel/tests/test_sanma.py
  ✅ 35 行全部对上（荣和 35 格 + 自摸 33 格 + 亲家荣和 35 格）
```

顺带解释两个「—」：**2 番 25 符自摸**和 **1 番 110 符自摸**在表里是空的，
因为这两个牌型根本不可能出现（七对子自摸必带门前清自摸和 → 至少 3 番；
110 符只可能来自门清高符手 → 至少 2 番）。

## 二、模块结构

```
aimodel/
├── sanma.py        三麻规则内核：和牌判定 / 役种 / 符与点数
├── fastshanten.py  快速向听·进张（分花色块 + 帕累托剪枝）
├── engine.py       对局引擎：摸打 / 副露 / 拔北 / 立直 / 流局 / 算点
├── encode.py       局面 -> 特征向量（含「每张候选牌」的动作特征）
├── net.py          纯 numpy 神经网络（策略多头 + 价值头 + 动作塔）
├── agents.py       随机 / 启发式教师 / 神经网络 / 人类 四种 agent
├── train.py        行为克隆 + 自对弈 PPO
├── evaluate.py     对战评测（座位轮换 + 配对检验）
├── play.py         终端对局脚本（可人机对战）
├── advise.py       截图 -> 出牌建议（接外层识图）
├── ui/             三人对战台（浏览器 UI + 外部接口 + 自动托管）
└── tests/          规则 / 向听 / 引擎 / 特征 / 网络 五套测试
```

### 为什么要自己写快速向听

外层工程已有 [`potatomaj.shanten`](../potatomaj/shanten.py)（写得清楚、改得动），
但一次向听 230 µs、一次进张 80 ms —— 生成几万条训练数据根本跑不动。
`fastshanten.py` 换成「按花色分块枚举 + 帕累托剪枝 + 缓存」：

| | 一次向听 | 一次进张 |
|---|---|---|
| `potatomaj.shanten` | 231 µs | 80 ms |
| `aimodel.fastshanten` | **4~30 µs** | **0.14 ms** |

正确性不是「看起来对」：两个实现是**各自独立写**的，测试里逐手交叉验证
（13 张 × 400 手、14 张 × 150 手、进张集合 12 手）**零处不一致**，
另外还验证了「直接算块分解」== 「逐张弃牌取最优」400 手。

### 特征怎么给

网络看到两层特征：

1. **全局**（485 维）：自己手牌/副露/牌河、两家牌河与副露、可见牌计数、
   宝牌指示牌与宝牌、点数、巡目、立直一发、拔北、向听 one-hot、进张枚数…
2. **动作**（每张候选牌 11 维）：**打掉它之后几向听、打掉它之后的进张枚数、
   危险度、是否现物、是否宝牌/赤牌/役牌、还剩几张、是否摸切、是否孤张**

第二层是后来加的，也是这一版明显变强的关键：只给全局特征时，网络得自己从
34 维计数里"悟"出「打这张会退向听」「这张打出去很危险」，
防法学得特别慢；把这两件事直接算好当特征喂进去，等于把牌效和读牌的先验
交给它，剩下的（什么时候弃和、贪不贪）才是真正要学的。

## 三、训练

两阶段：

1. **行为克隆**：让启发式教师打几千局，把它的每一步决策都学下来
   （打牌 / 立直 / 碰杠 / 拔北 / 和牌 各有独立的策略头）。
   纯强化学习从随机权重起步在三麻这种「一局几十个决策、奖励还稀疏」的
   环境里几乎不可能收敛，先克隆出牌效才有意义。
2. **自对弈 PPO**：对手池 = 当前网络（70%）+ 教师（25%）+ 上一版快照（5%），
   奖励 = 整场点数变化（含立直棒），优势 = 回报 − 价值头预测，
   截断目标 + 熵正则。

## 五、已知限制

诚实列一下这一版没做的：

* **没有实现**：人和、流し満貫、责任払い（大三元/大四喜包牌）、
  南入/西入延长战（`Rule.sudden_death` 开关默认关）、虚聴判定、形式听牌之外的细节
* **抢杠**只在加杠时判定；拔北被荣和实现了，但没有实现「拔北后不能再拔」的连锁限制
* 局面里读不到的场况（点数、立直状态）在 `advise.py` 里只能按默认值假设，
  所以截图建议只是**牌效参考**，不能代替读牌
* 网络是 MLP，没有用 Transformer / CNN；麻将其实是「不定长 + 置换不变」的
  结构，理论上换个网络结构还有不少空间
