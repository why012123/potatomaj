## 七·五、🔴 技术路线修正（2026-10-21 实测 Mortal 权重之后 —— 这条推翻了我原来的「堆到 10M 参数」）

### 实测数据（不是资料，是把 `mortal.pth` 拆开数的）

```
Mortal v4 策略网络：
  Conv1d(1012 -> 32, k=3) + ResBlock(32ch) x 2 + Conv1d(32 -> 32)
  + Linear(1088 -> 1024) + DQN 头(1024 -> 1 + 47 动作)
  参数量 = **1,228,649**（1.23M）+ DQN 头 48,128
  其中 **Linear(1088->1024) 一层就占 1,114,112（90%）**
  权重文件 5.1 MB；config 原文 {'resnet': {'conv_channels': 32, 'num_blocks': 2}}
  输入 = **1012 维 ≈ 34 张牌 × 每张 ~30 个特征（含历史打牌序列/立直/可见牌/宝牌）**
```

### 三条结论（直接改我们的设计与目标）

```
① **参数量不是瓶颈**：Mortal 用 1.23M 参数到天凤 8-9 段 ✓
   -> 立项书的「参数量 >= 10M」是错的 ✗ 改成 **1~3M** ✓
   （我们自己的实测也一直指向同一件事：>20M 参数、没有历史特征 = 白搭）
② **特征的组织方式才是瓶颈**：Mortal 是「**按牌位组织的特征张量 + 对牌位做一维卷积**」✓
   我们是「平铺的 645 维全局向量」✗ 没有历史序列 ✗
   -> dot V1 的网络输入改成 **(34 牌位 × F 特征) 的张量**，第一层用 Conv1d + 残差块 ✓
   -> 目标 F ≈ 30（对齐 Mortal 的 1012），先从 20 起步 ✓
③ **数据规模与训练配方**：Mortal 是几十亿样本级 SFT + RL，我们 2.3M 条 = 千分之一 ✓
   -> 所以「数据」仍是 dot V1 的第一优先级 ✓（鳳凰卓 5,717 局已验证：同步数下 +1.72）
```

### 对 P3 阶段的具体改法

| 原计划 | 改成 |
|---|---|
| 10M+ 参数 MLP/ResNet on 645 维 | **1~3M 参数 Conv1d-ResNet on (34 × F) 张量** |
| 输入 = 现有 encode() | 输入 = 新的 per-tile 特征（hand/visible/dora/history/危险度/立直状态，每张牌一份） |
| 先训大模型再考虑特征 | **先改特征布局，再谈规模** ✓ |

> ⚠️ 这不影响 pro4v1.2（它继续用 645 维平铺特征）✓
> 影响的是 dot V1 的网络定义与第一周的工作顺序：**P0 从「训练器」变成「per-tile 特征 + Conv 网络」** ✓

## 八、边下边训：**可以 ✓ 但必须用「快照 + 增量」**（补写于 2026-10-21，用户提出）

### 为什么不能直接「一直训下去」✗

```
坑：数据集在训练中途**变大** ✗
  -> 训练器读到一半数据变了 ✗ loss 曲线会莫名其妙跳 ✗
  -> 而且「这个模型是用多少数据训的」说不清 ✗ 复盘不了 ✗
```

### 正确做法：**快照（snapshot）**

```
① 下载继续跑（单会话 ✓ 后台 ✓ 只占 ~1 核 ✓ 对 GPU 训练几乎无影响 ✓）
② 每隔几天，把**当前已下载的全部牌谱**抽成一个**不可变数据集快照** ✓
   命名带局数：`_data/majdot/snap_320k.npz` ✓
③ 训练只读**快照** ✓ 快照生成后**绝不修改** ✗
④ 下一个阶段用更大的快照 ✓ 从上一个 checkpoint **继续训**（不是从零 ✗）
```

### 时间表（按实测速率 0.93 局/秒 ≈ **8.0 万局/天**）

| 天 | 累计牌谱 | 快照 | 训练内容 |
|---|---|---|---|
| 0–3 | 0 → 24 万 | — | PyTorch 训练器 + 管线验证（用旧 8 万局 ✓） |
| 3 | **约 32 万**（含旧 8 万） | `snap_320k` | 10M 参数首训 ✓ |
| 4–10 | → 88 万 | — | 训 `snap_320k` → checkpoint A ✓ |
| 10 | **约 88 万** | `snap_880k` | 从 A 继续 ✓ |
| 11–18 | → 150 万（超出目标 ✓） | — | 训 `snap_880k` → checkpoint B ✓ |
| 18 | **约 100 万+** | `snap_1M` | 从 B 继续 ✓ |
| 19–26 | — | — | 训 `snap_1M` → 最终模型 ✓ + 搜索（P5） |
| 27–30 | — | — | 配对赛 + 报告 ✓ |

### 关键设计选择（都有理由 ✗ 别随便改）

```
· **快照只增不改** ✓ 否则复盘不了 ✗
· **从上一个 checkpoint 继续** ✓ 而不是每次从零 ✗（省 5~10 天 ✓）
· 换快照时**重置学习率**（重新 warmup ✓）—— 数据分布略变 ✓ 学习率沿用旧的会震荡 ✗
· 旧快照**保留** ✓（至少留最近 2 个 ✓ 出问题要能回退 ✓）但要删更老的 ✓（省空间 ✓）
· 下载器只用 **1 核** ✓ 不吃 GPU ✓ -> 和训练**真并行** ✓
```

### 这样做的额外好处 ✓

```
每个快照都产出一个**可评估的 checkpoint** ✓
-> 我们能画出「数据量 -> 强度」的曲线 ✓
-> 这是回答「扩数据到底值多少」的直接证据 ✓
   （今天只有旧结论 ✗ 这次能拿新数字 ✓）
```
