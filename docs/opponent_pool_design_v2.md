## 2) 隔离（按 mac 的裁断，**三层叠加**）

### 第 1 层：接口层 —— 让误用在**类型层就不可能**

```python
@dataclass(frozen=True)
class PoolView:
    kind: Literal["select"]                 # ⚠️ **只有 "select" 一个取值** ✗
    members: tuple[str, ...]                # 对手 id
    # 构造时断言：members 与 HOLDOUT 名单**无交集** ✓
```
```
`select_best()` 的签名**只接受 `PoolView`** ✓
-> 拿不到「带 holdout 的 PoolView」✓（构造就会抛 ✓）
-> 「误用」不是靠人记得 ✗ 是**类型层做不到** ✓
```

### 第 2 层：运行期断言 —— 每次选择后当场自检

```
每次选择后断言：「本轮用到的对手 id 里没有 holdout 成员」✓
不通过 -> **抛异常并中止本次选择** ✗（不是打日志继续 ✓）
理由：宁可这一轮不选 ✓ 也不要选一个被污染的 ✓
```

### 第 3 层：⭐ 审计日志 —— **mac 说这层最重要**

```
每次选择写一行 `_data/selection_audit.jsonl`：
    {轮次, 用到的对手 id 列表, 判据, 结果, kl_coef, 是否回滚, K}

⭐ 关键（mac 的原话，我抄下来）：
   「『我们不违反』是**承诺** ✓
     『**日志能证明我们没违反**』才是**隔离** ✓」
```
**为什么这层最重要** ✗：
```
前两层防的是「**我们自己**手滑」✓
第 3 层防的是「**别人无法验证**」✗
-> 没有它，隔离是**内部信任** ✓ 有了它，隔离是**可外部验证的** ✓
```
**⭐ 而这和「dump 打印来自哪个工作树」是同一个手法** ✓
```
让违规**看得见** ✓ 而不是要求人不违规 ✓
-> 我先前那条假对照（两边其实是同一份代码）✗
   之所以被发现，正是因为脚本**打印了来源** ✓
```

### 保留我附录A 里那个「指纹机制」✓（它是机械可验的 ✓）

```
`pool_holdout.json` 的 members 有 sha256 指纹存 `pool_holdout.sha256` ✓
-> 换成员 -> 指纹不匹配 -> 测试红 ✓
-> 「悄悄换尺子」变成「一次显式、有记录的改动」✓
```

**⚠️ 我仍然承认的边界** ✗（v1 里说过 ✓ 保留 ✓）：
```
以上三层都**不是密码学隔离** ✓ 能绕开 ✓（写中转文件、动态 import ✓）
它挡的是**手滑** ✓（真实风险的绝大多数 ✓）
**刻意的绕开不是本项目的威胁模型** ✓（这里没有对手 ✓
 只有「未来的自己忘了」和「另一个 agent 不知道」✓）
-> 第 3 层把「能绕开」提升成「**绕开会留痕**」✓ 这已经够用 ✓
```
**我不建议上「进程级隔离（ACL）」** ✗ —— 成本/收益比差 ✓（v1 已述 ✓）

## 3) K 的取值（按 mac 的裁断）

```
**K 是参数** ✓ 不是常数 ✗
首轮：K = 25 ✓（由 +0.09/轮、MDE +2 推得 ✓）
⚠️ 但它隐含「增益线性」✗ —— RL 增益通常**递减** ✓
⚠️ 而且**池子上线后每轮增益会变** ✗（方向未知：池子有信息量 -> 可能变大 ✓；
   对手更强 -> 可能变小 ✓）
-> **第二轮起按实测增益重推** ✓（可能落到 5~10 ✓）
-> **两次 K 都记进审计日志** ✓
```

**⚠️ 补我自己的更正** ✗（附录B ✓ 保留 ✓）：
```
点估计「预期增益 > MDE」**不保证检得出** ✓（那是概率命题 ✗）
-> 报 K 时必须同时报**裕度** ✓
   首轮 K=25 的裕度只有 **1.18×** ✓（我算过 ✓）-> **标为「待验证」** ✓
   若要裕度 ≥ 2× -> K 需约 40 ✓
-> **裁断建议**：首轮用 **K=25 但明确标注裕度 1.18×、结果待验证** ✓
   或直接 **K=40**（裕度 1.89× ✓ 代价：一夜从 2.7 代降到 1.7 代 ✓）
   **我倾向后者** ✓ 但这是 captain 的取舍 ✓
```

## 5) ⭐ mac 新增的第 ④ 条：**池子本身也要问「可回收」**

```
他原话：对手池的价值 = 「**RL 能因为它涨多少**」✗ 不是「池子有多大」✓
-> 形状⑬（耗时占比 ≠ 可回收占比）**用在池子上** ✓ 且要**逐层剥** ✓
```
**所以首轮用最小池** ✓：
```
SELECT **6 个** / HOLDOUT **3 个** ✓
量出**增益**再决定要不要扩 ✓
```
**⚠️ 而这条正是我 42% -> 12% 那次的教训** ✓ **只是换到了「池子」这个尺度** ✓
```
我那次：把「成本占比」当「可回收」✗ 只剥了一层 -> 高估 3.5 倍 ✓
这次：不许把「池子大小」当「增益」✗
-> **先量增益** ✓ 而且要**逐层剥**：
   池子大小 -> 每类对手的贡献 -> 每类里「必要/冗余」-> 只有冗余那部分可回收 ✓
```

## 7) 验收（**怎么知道对手池真的有用**）

```
主判据：对 **HOLDOUT** 的配对赛（同牌山 + SPRT ✓ 与三杠杆排序同协议 ✓）
对照：  **同起点、同预算、无池**（= 纯自对弈 ✓）
判据：  `有池 vs 无池` 的 **Δ 段位分** 与 **p 值** ✓
**并预设「若不显著」怎么办** ✗：
  不显著 -> 不许说「有用」✗ 也不许说「没用」✗

（这是我们反复踩过的：**不说清 MDE 就没法解释不显著** ✓）
```
